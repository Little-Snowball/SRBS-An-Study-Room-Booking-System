## 1. 引言

### 1.1 编写目的

本文档旨在明确“自习室预约系统”的功能边界、业务流程、数据需求及非功能性约束，解决课程设计第一阶段“我们要做什么？为什么做？”的核心问题。本文档预期读者包括项目指导教师、项目经理、前端开发工程师、后端开发工程师及测试工程师，作为后续系统设计、数据库建模、编码实现与测试验收的基准依据。

### 1.2 项目背景（为什么做）

在高校日常教学管理中，图书馆与公共自习室长期面临以下管理痛点：

1. **资源浪费严重**：“用书本占座却整日不来”的现象普遍，导致座位实际使用率远低于账面占用率。
2. **信息不对称**：学生无法提前获知各教学楼自习室的实时余位情况，高峰期（如期末周、考研季）寻座耗时费力。
3. **冲突与管理成本高**：线下抢座易引发纠纷，且管理员依靠人工巡检清理占座的效率极低、缺乏客观依据。

为此，本项目构建一套数字化的**自习室预约系统**，通过“分时预约 $\rightarrow$ 现场签到 $\rightarrow$ 暂离管控 $\rightarrow$ 违约扣分与自动释放”的闭环机制，提高公共学习空间的周转效率与管理规范化水平。

### 1.3 术语定义

* **预约时段（Time Slot）**：学生申请使用某个座位的起止时间区间，记为 $[T_{\text{start}}, T_{\text{end}}]$。
* **签到宽限期（Grace Period）**：允许学生在预约开始时间 $T_{\text{start}}$ 前后完成签到的有效时间窗口，记为 $[T_{\text{start}} - \Delta t_1, T_{\text{start}} + \Delta t_2]$。
* **暂离（Temporary Leave）**：学生在已签到状态下因就餐、接水等原因短暂离开，系统为其保留座位使用权一段受限时间 $\Delta t_{\text{leave}}$。
* **信用分（Credit Score）**：衡量学生履约情况的量化指标，初始值为 $100$ 分，发生爽约或超时未签退时按规则扣减，低于阈值 $S_{\text{min}}$ 时触发预约限制。

## 2. 项目总体概述

### 2.1 系统总体定位

本系统采用前后端分离的 Web 架构（支持 PC 端与移动端浏览器自适应访问），面向全校师生及后勤教务管理人员提供在线选座、考勤打卡、信用监管与运营统计服务。

### 2.2 用户角色与特征

| 角色名称         | 用户特征                                               | 核心业务诉求                                            |
|:------------ |:-------------------------------------------------- |:------------------------------------------------- |
| **学生（普通用户）** | 高校在校学生，熟悉移动互联网操作，在备考或日常学习中有高频订座需求。                 | 快速筛选心仪座位（如带插座、靠窗）、公平预约、便捷签到/暂离/签退、透明查看个人信用分与预约历史。 |
| **系统管理员**    | 图书馆或教务后勤管理人员，关注空间秩序与整体利用率。                         | 灵活配置自习室平面座位与开放时间、动态调整预约与扣分规则、处理异常违约申诉、查看数据统计报表。   |
| **系统定时服务**   | 后台自动化调度进程（非人工角色），按固定时间粒度（如每 $1\text{ min}$）扫描订单状态。 | 自动识别超时未签到、暂离超时、到期未签退等订单，执行状态流转、座位释放与信用扣分。         |

### 2.3 假设与依赖

* 假设所有使用系统的学生均已拥有学校统一分配的学号与初始认证信息。
* 假设自习室现场具备基本的网络覆盖，支持学生使用手机或电脑完成签到操作。
* 系统依赖关系型数据库（如 MySQL）保证事务ACID特性，并依赖服务端统一时钟作为考勤判定的唯一时间基准（不信任客户端本地时间）。

### 3.2 核心用例详细规约

#### （1）UC-03：提交座位预约

* **用例编号**：UC-03

* **主要参与者**：学生

* **前置条件**：学生已完成登录认证（UC-01），且当前账号未被锁定。

* **后置条件**：系统生成一条状态为“待签到（`RESERVED`）”的预约记录，对应座位在该时段内对其他用户显示为“已占用”。

* **基本事件流（成功场景）**：
  
  1. 学生选择目标日期、预约起止时段 $[T_{\text{start}}, T_{\text{end}}]$ 及目标自习室。
  
  2. 系统过滤并展示该时段内所有状态正常的自习室座位列表及属性（是否有电源、是否靠窗）。
  
  3. 学生选中目标座位并点击“立即预约”。
  
  4. 系统触发包含用例 **UC-04（校验信用分与时段冲突）**：
     * 校验学生当前信用分 $S_{\text{current}} \ge S_{\text{min}}$（默认 $S_{\text{min}} = 60$）；
     * 校验预约时长 $T_{\text{end}} - T_{\text{start}} \le D_{\text{max}}$（默认单次最长 $4\text{ h}$）；
     * 校验该学生在同一时段内无其他有效预约；
     * 校验该座位在 $[T_{\text{start}}, T_{\text{end}}]$ 时段内未被其他有效订单占用。
  
  5. 校验全部通过后，系统在数据库事务中写入预约记录，返回“预约成功”提示及签到截止时间。

* **异常/备选事件流**：
  
  * **4a. 信用分不足**：若 $S_{\text{current}} < S_{\text{min}}$，系统拒绝预约并提示“当前信用分低于 $60$ 分，处于限制预约期”。
  * **4b. 时段冲突**：若学生本人已有重叠时段的预约，系统提示“您在该时段已有生效中的预约，请勿重复占座”。
  * **4c. 并发抢座冲突**：若多个学生同时提交同一座位的重叠时段预约，同一事务内锁定座位资源行并执行时段冲突查询，拦截后到达的请求，提示“手慢了，该座位刚刚已被其他同学预约，请重新选择”。

#### （2）UC-06 现场签到确认 & UC-09 超时释放与违约扣分

* **用例编号**：UC-06 / UC-09

* **主要参与者**：学生、系统定时服务

* **前置条件**：存在状态为“待签到（`RESERVED`）”的预约订单。

* **后置条件**：订单状态更新为“使用中（`IN_USE`）”或“已违约释放（`VIOLATED`）”。

* **基本事件流（正常签到）**：
  
  1. 学生在签到有效窗口 $[T_{\text{start}} - 15\text{ min}, T_{\text{start}} + 15\text{ min}]$ 内到达自习室。
  
  2. 学生进入“我的预约”页面，点击“立即签到”，输入自习室 6 位数字现场签到码。
  
  3. 系统核对当前服务端时间 $T_{\text{now}}$ 处于有效窗口内且 6 位签到码匹配。
  
  4. 系统将订单状态修改为“使用中（`IN_USE`）”，记录实际签到时间 $T_{\text{check\_in}}$。

* **扩展事件流（超时未到自动释放）**：
  
  * **3a. 超过签到宽限期未操作**：当服务端时间 $T_{\text{now}} > T_{\text{start}} + 15\text{ min}$ 且订单仍为“待签到（`RESERVED`）”时：
    
    1. 系统定时任务捕获该超时订单，将其状态强制变更为“已违约（`VIOLATED`）”。
    
    2. 立即释放该座位在 $[T_{\text{now}}, T_{\text{end}}]$ 的剩余时段资源供其他同学预约。
    
    3. 扣减该学生信用分 $\Delta S = 10$ 分，并生成一条信用变动流水记录。

## 4. 详细功能需求

### 4.1 学生端功能模块

#### 4.1.1 个人中心与认证模块

* **FR-S01 学号登录与注销**：支持学号与密码登录，登录成功后签发 JWT 令牌；支持安全退出。
* **FR-S02 个人信息与信用概览**：展示学生姓名、学号、学院、当前信用分数值、信用等级状态（正常/受限）及近期违约次数。

#### 4.1.2 座位检索与可视化选座模块

* **FR-S03 多维条件筛选**：支持按日期（当天或未来 $N$ 天，默认 $N = 2$）、起止时间段（以 $30\text{ min}$ 为最小时间刻度）、校区/教学楼、座位特性标签（靠窗、带插座、静音区）筛选可用座位。
* **FR-S04 座位状态可视化展示**：以网格平面图或卡片列表形式展示自习室座位，使用不同颜色区分“空闲可选（绿色）”、“已被预约（黄色）”、“使用中（红色）”、“维修停用（灰色）”。

#### 4.1.3 预约与考勤流转模块

* **FR-S05 预约提交与冲突拦截**：校验预约时长上限（如 $0.5\text{ h} \le \Delta T \le 4\text{ h}$）与个人时段唯一性，完成预约锁座。
* **FR-S06 预约提前取消**：在 $T_{\text{now}} \le T_{\text{start}} - 15\text{ min}$ 前允许学生无责取消预约，订单状态变为“已取消（`CANCELLED`）”，座位即刻释放。
* **FR-S07 到场签到**：支持在 $[T_{\text{start}} - 15\text{ min}, T_{\text{start}} + 15\text{ min}]$ 内输入自习室 6 位数字现场签到码完成签到激活。
* **FR-S08 暂离与归来打卡**：处于“使用中（`IN_USE`）”状态的学生可点击“暂离”，订单状态变为“暂离中（`LEFT_TEMP`）”，系统启动倒计时（默认 $\Delta t_{\text{leave}} = 30\text{ min}$）；学生在倒计时结束前点击“恢复使用”则回到“使用中”状态。
* **FR-S09 主动签退**：学生学习结束时点击“签退”，订单状态变为“已完成（`COMPLETED`）”，若提前签退则自动释放剩余时间段的座位可约状态；正常签退时按履约时长累计信用奖励：单次自习满 $2\text{ h}$ 奖励 $+2$ 分，此后每满 $30\text{ min}$ 再加 $1$ 分，单次自习最多奖励 $+5$ 分；信用分上限为 $100$ 分，奖励仅用于恢复此前被扣减的信用分，已达上限时不再累加。

#### 4.1.4 信用记录与违约申诉模块

* **FR-S10 信用流水查询**：按时间倒序展示每一次扣分与加分的原因、关联订单号、变动分值及变动后余额。
* **FR-S11 违约在线申诉**：针对因突发疾病、校园断网等不可抗力导致的违约扣分，学生可在违约发生后 $48\text{ h}$ 内提交文字说明与凭证发起申诉。

### 4.2 管理员端功能模块

#### 4.2.1 空间与座位配置模块

* **FR-A01 自习室管理**：支持新增、编辑、停用/启用自习室，设置自习室名称、所属楼宇、开放起止时间（如 `07:00` 至 `22:30`）、总座位数及 6 位数字现场签到码。
* **FR-A02 座位批量生成与状态维护**：支持按行列坐标 $(R_i, C_j)$ 批量生成座位编号，单独配置每个座位的属性标签（插座/靠窗）及物理状态（正常/损坏停用）。当某座位被设为“损坏停用”时，系统自动取消该座位后续未开始的预约并通知学生。

#### 4.2.2 规则引擎与信用监管模块

* **FR-A03 预约参数动态配置**：管理员可在后台修改全局规则参数，包括：最大提前预约天数、单次最长预约时长、签到宽限期分钟数、暂离最长分钟数、各类违约扣分分值及限制预约的信用分阈值。
* **FR-A04 违约申诉审核**：管理员查看待审核的申诉工单，选择“通过”或“驳回”。若审核通过，系统自动撤销对应违约记录（置为“已撤销”，不物理删除）并将扣减的信用分退回学生账户，同时生成一条返分流水。
* **FR-A05 信用人工修正与黑名单管理**：支持管理员对特定异常账户进行信用分重置或手动解除限制。

#### 4.2.3 统计报表与公告模块

* **FR-A06 运营数据可视化看板**：统计并展示今日预约总人次、当前在座率、各时段流量折线图、各教学楼自习室使用率排行及本周违约率占比。
* **FR-A07 系统公告发布**：发布自习室临时闭馆、考试周开放时间调整等通知公告，在学生端首页置顶展示。

## 5. 数据需求与核心实体设计

系统需持久化存储以下核心业务实体（为第二阶段数据库设计提供输入）：

1. **用户实体（`User`）**：用户ID、学号/工号（唯一）、密码哈希、姓名、角色（学生/管理员）、手机号、当前信用分（默认 $100$）、账号状态（正常/受限/禁用）、创建时间。
2. **自习室实体（`StudyRoom`）**：自习室ID、房间名称、所属教学楼、楼层、每日开放时间、每日关闭时间、总行数、总列数、6 位数字签到码、房间状态（开放/闭馆）。
3. **座位实体（`Seat`）**：座位ID、所属自习室ID、座位编码（如 `A-01`）、行号、列号、是否有插座（布尔值）、是否靠窗（布尔值）、座位状态（正常/维修中）。
4. **预约订单实体（`Reservation`）**：订单ID、订单流水号、用户ID、自习室ID、座位ID、预约日期、开始时间 $T_{\text{start}}$、结束时间 $T_{\text{end}}$、订单状态（`RESERVED`待签到 / `IN_USE`使用中 / `LEFT_TEMP`暂离中 / `COMPLETED`已完成 / `CANCELLED`已取消 / `VIOLATED`已违约）、实际签到时间、最近暂离时间、实际签退时间、创建时间。
5. **信用流水实体（`CreditLog`）**：流水ID、用户ID、关联订单ID、变动类型（爽约未签到扣分/暂离超时扣分/未签退扣分/履约奖励加分/申诉恢复加分）、变动分值（正负数）、变动后信用分、变动原因说明、记录时间。
6. **违约申诉实体（`Appeal`）**：申诉ID、关联信用流水ID、关联订单ID、申请人ID、申诉理由、审核状态（`PENDING`待审核 / `APPROVED`已通过 / `REJECTED`已驳回）、审核管理员ID、审核意见、提交时间、审核时间。
7. **系统规则配置实体（`SysConfig`）**：配置项Key、配置项名称、配置项数值、单位说明、更新时间。

## 6. 非功能性需求

### 6.1 数据一致性与并发控制需求（核心考核点）

* **时段重叠判定逻辑**：对于同一座位，设已有有效预约（状态为 `RESERVED`、`IN_USE` 或 `LEFT_TEMP`）的时段为 $[A_{\text{start}}, A_{\text{end}}]$，新申请的预约时段为 $[B_{\text{start}}, B_{\text{end}}]$。当且仅当满足以下不等式时，判定两个时段存在冲突：
  $$\max(A_{\text{start}}, B_{\text{start}}) < \min(A_{\text{end}}, B_{\text{end}})$$
* **防并发超卖**：在整点放号或期末高峰期，当多个用户同时请求同一座位的重叠时段时，后端必须通过锁定 `Seat` 行（`SELECT ... FOR UPDATE`）并在同一数据库事务内重新判断预约时段是否重叠，或使用离散时隙唯一约束等可证明正确的机制，确保最终仅有 $1$ 个请求预约成功，其余请求准确返回冲突提示，严禁产生脏数据。

### 6.2 性能需求

* **页面加载与常规查询**：自习室列表及座位状态平面图查询接口的平均响应时间应满足 $T_{\text{resp}} \le 500\text{ ms}$。
* **并发处理能力**：系统应支持至少 $100$ 个并发虚拟用户同时执行选座与签到操作，接口请求成功率 $\ge 99.5\%$。

### 6.3 安全性需求

* **身份鉴权与越权防护**：除登录与公开公告接口外，所有 API 均需校验 JWT 令牌；严格区分学生与管理员权限，防止学生通过构造请求调用管理员接口（垂直越权）或操作其他学生的预约订单（水平越权）。
* **敏感数据保护**：用户密码在数据库中严禁明文存储，必须采用 BCrypt 或 Argon2id 等专用密码哈希算法存储（哈希不可逆，不属于加密）。

### 6.4 可维护性与演化需求

* **遵循软件工程规范**：代码需具备清晰的模块分层（Controller $\rightarrow$ Service $\rightarrow$ DAO/Mapper），关键业务逻辑（如状态机流转、冲突检测）需编写详细的文档注释与单元测试，以便在课程中后期出现“需求变化”时能够快速定位并完成软件维护与演化。

### 7.3 预约订单状态与可用性

`RESERVED（待签到） → IN_USE（使用中） → COMPLETED（已完成）`

- `RESERVED → CANCELLED`：学生在允许时间内取消，释放其未来尚未使用的时间段。
- `RESERVED → VIOLATED`：签到截止后仍未签到，扣分并从当前时刻起释放剩余时段。
- `IN_USE → LEFT_TEMP → IN_USE`：暂离与按时回座；`LEFT_TEMP → VIOLATED`：暂离超时后的处置方案须确认。
- `IN_USE / LEFT_TEMP → COMPLETED`：预约结束前主动签退，保留历史订单，释放尚未使用的后续时段。
- 预约结束时间到达后仍未签退：建议由定时任务进行终态结算，是否扣分及扣多少按评审确认后的规则配置执行。

**重要区别：**订单历史不会被物理删除。所谓“释放座位”指不再占用未来的预约可用时段；当前时刻之前的历史预约记录仍然保留。事务必须确保同一座位在任意重叠有效时段内最多只有一笔有效预约。

## 8. 数据逻辑与接口约定（补充）

### 8.1 数据完整性

1. 用户学号唯一；管理员/学生角色不可由前端请求自行提升。
2. 房间内座位编号唯一；只有正常、开放中的座位可预约。
3. 订单存储完整开始/结束日期时间并建立索引（如座位 ID + 时段与状态），跨天订单本期不支持。
4. 信用调整全部以流水记录留痕，不做物理删除：申诉通过时系统自动撤销对应违约记录（置为“已撤销”）并退回被扣减的信用分，同时生成一条返分流水；重复审核、重复定时执行不得重复扣分或返分。
5. 订单状态变更须携带版本或做条件更新，确保取消、签到、超时扫描并发时最多有一次成功状态迁移。

### 8.2 预约并发事务伪流程

```text
BEGIN TRANSACTION
  SELECT id FROM seat WHERE id = :seatId FOR UPDATE;
  检查座位/房间是否开放、用户信用及预约时长是否合法；
  查询同一座位存在 start_time < :newEnd 且 end_time > :newStart 的有效订单；
  查询同一用户是否有重叠的有效订单；
  若存在冲突 -> ROLLBACK、返回 409 Conflict；
  否则 INSERT 新订单 -> COMMIT；
END
```

**注意：**一般的 `(seat_id,start_time,end_time)` 唯一索引**无法**阻止不同起止时间之间的重叠预约。因此必须在串行化的资源锁定或等价时隙约束内验证冲突。若还需阻止同一学生对不同座位并发预约，同一事务中应固定顺序锁定用户资源行或采用其他可证明一致的互斥机制。

# 自习室预约系统——项目开发计划

| 项目属性 | 内容 |
|:---|:---|
| 项目名称 | 高校自习室预约与考勤管理系统 |
| 计划版本 | V1.0（8 周） |
| 项目类型 | 软件工程综合实践：前后端分离 Web 系统 |
| 适用团队 | 3 人（已确认） |
| 版本管理 | Git / GitHub |
| 时间基准 | W1—W8 共 8 周（已确认）；具体日历日期按课程安排填写 |

## 1. 目标与交付范围

### 1.1 项目目标

以校园自习室为对象，建立学生端与管理员端共用浏览器的在线预约与考勤管理系统。完整经历**选题—需求—设计—实现—测试—验收**软件工程过程，形成可追踪需求、可运行软件、可复现测试证据及项目总结。

### 1.2 验收的最小业务闭环

**登录 → 查询可用座位 → 提交分时预约 → 现场签到 → 主动签退 / 超时自动释放 → 历史订单可查询**。管理端至少能够维护自习室与座位，且学生端无法越权访问管理员 API。对同一座位重叠时段的并发预约，必须保证只有一个请求成功。

### 1.3 优先级与范围控制

| 优先级 | 内容 | 退出准则 |
|:---|:---|:---|
| P0 必须 | 鉴权、角色权限、座位检索、预约事务、签到/签退、超时释放、资源维护 | 主链路联调通过且无重叠有效订单 |
| P1 推荐 | 暂离回座、信用流水、申诉审核、规则配置 | 状态迁移与信用幂等测试通过 |
| P2 扩展 | 运营图表、公告、批量座位标签与优化 UI | 不阻塞 P0/P1 交付 |

## 2. 技术方案与环境（待团队确认）

| 层次 | 推荐方案 | 理由 |
|:---|:---|:---|
| 前端 | Vue 3、Vite、Vue Router、Element Plus | 双角色页面复用、开发快、适合课程演示 |
| 后端 | Java 17、Spring Boot 3、Spring Security、MyBatis/JPA（二选一） | 身份鉴权、事务、定时任务和接口测试成熟 |
| 数据库 | MySQL 8 | 事务与行锁，支持预约并发一致性 |
| 接口联调 | REST/JSON、OpenAPI/Swagger、Postman | 接口与测试可复现 |
| 质量工具 | Git、GitHub、JUnit、接口测试工具、基础负载测试 | 支持代码审查和第三阶段测试汇报 |
| 部署 | 单机开发机或云主机、前端静态构建、后端服务、数据库 | 不引入课程范围外的微服务复杂度 |

技术选型为**建议而非源方案既定事实**；在 W2 评审后冻结，并在《系统设计说明书》中明确最终版本。

## 3. 组织结构、职责与协作

### 3.1 责任分配（3 人）

| 职位代号 | 主要职责 | 主要交付 |
|:---|:---|:---|
| R1 组长/需求与测试统筹 | 范围管理、SRS、用例、需求评审、接口与集成测试、缺陷跟踪、部署脚本、答辩协调 | SRS、计划、需求追踪矩阵、测试报告 |
| R2 前端负责人 | 学生/管理员页面、路由鉴权、交互和原型 | UI 原型、前端源代码、页面测试 |
| R3 后端与数据负责人 | 数据库建模、预约事务、冲突检测、订单状态机、定时任务、信用申诉、管理员接口 | ER 图、SQL、核心业务接口、并发测试 |

本项目按 3 人组队：已将原 5 人示例中的 R1+R5 合并为“组长/需求与测试统筹”、R3+R4 合并为“后端与数据负责人”，并相应压缩 P2 范围。**最终成员姓名与责任归属必须在实际立项后填写。**

### 3.2 开发协作约定

- Git 主分支 `main` 保持可演示；开发走 `feature/*` 分支和 Pull Request；合并前至少一名同伴审阅。
- 每周至少 1 次组会记录已完成事项、阻塞问题、决策和下周计划。
- 所有功能都关联需求 ID、任务 ID、提交 ID 和测试用例 ID，避免出现“完成了页面但未覆盖需求”。
- 数据库表结构变更使用版本化 SQL 文件，开发环境须支持一键初始化最小演示数据。

## 7. 测试计划、质量度量与验收

### 7.1 测试分层

| 层级 | 测试重点 | 证据形式 |
|:---|:---|:---|
| 单元测试 | 时间段重叠算法、扣分阈值、订单合法迁移、幂等事件 | 测试代码与执行结果 |
| 接口测试 | 登录、房间查询、预约/取消/签到/暂离/签退、申诉审核 | Postman 集合或自动化脚本 |
| 集成测试 | 页面—API—数据库和定时任务跨模块配合 | 场景脚本与运行截图 |
| 安全测试 | 非法令牌、角色越权、操作他人订单、SQL 注入等 | 请求/响应与修复记录 |
| 并发测试 | 同座位、同学生不同座位同时预约 | 并发日志与数据库一致性查询 |
| 验收测试 | 教师指定用户故事、完整核心链路 | 演示录像/截图与签收清单 |

### 7.2 验收门槛（可按课程环境调整）

- 主链路中的 P0 用例全部通过；无阻断演示的高优先级缺陷。
- 并发预约测试保证“重叠有效订单数 = 0”，且冲突返回可理解的信息。
- 资源关闭/维修、超时扫描和申诉审核支持幂等执行。
- 明确记录测试机器配置、数据库版本、并发工具及样本规模，禁止只报目标而不报实测。
- 所有核心 API 完成角色/归属校验，测试端不能直接修改别人的预约和信用。

## 8. 风险台账与处置预案

| 风险 | 可能性/影响 | 预警条件 | 缓解策略 | 负责人 |
|:---|:---|:---|:---|:---|
| 多人并发导致座位超卖 | 中/高 | 同时抢座出现两笔订单 | W3 完成事务 PoC，W5 引入并发测试 | R3 |
| 订单状态或信用重复处理 | 中/高 | 双重扣分、重复签退 | 状态条件更新、信用事件幂等键、回归用例 | R3 |
| 业务规则变动造成返工 | 高/中 | W4 仍频繁修改时限 | W2 冻结规则基线，变更单评估影响 | R1 |
| 前后端接口不一致 | 中/中 | 联调反复报 404/字段缺失 | W3 OpenAPI 先行、模拟数据联调 | R2/R3 |
| 课程时间不足、功能过宽 | 高/中 | W5 主链路仍未跑通 | 先保 P0，将复杂图表列 P2 | R1 |
| 数据库或演示环境不可用 | 中/中 | 无法一键跑通部署 | 版本锁定、备份 SQL、README、演示录屏 | R1/R3 |

## 9. 需求变更与配置管理

每次需求变更记录：变更 ID、提出人、原描述、新描述、缘由、优先级、影响页面/API/表结构/测试、工时估计、组长确认及变更后版本号。W2 冻结首版需求，W6 联调后原则上只允许缺陷修复或教师要求的必要调整；所有变更需补回归测试。

## 10. 提交清单与答辩演示建议

**第一阶段：**SRS（含功能、非功能、业务规则、数据需求、验收条件）、UML 用例图、项目开发计划。

**第二阶段：**系统设计说明书（架构、模块、时序/状态图）、ER 图和数据字典、前端高保真原型、数据库脚本、前后端源码及阶段性运行软件。

**第三阶段：**完整可运行软件、测试计划和实测报告、缺陷统计、项目总结、部署 README、Git 过程证据、答辩演示流程。

演示建议按“学生查询余位—预约—管理员查看—学生签到—提前签退—再次预约同座位余下时段—模拟超时违约—管理员处理申诉”串联，并额外现场展示一次并发冲突测试。
